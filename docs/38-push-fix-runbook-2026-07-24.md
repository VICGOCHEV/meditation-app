# Relax Me — почему пуши доходят только разработчику. Разбор и безопасное решение

> Диагноз проблемы с Telegram-пушами и пошаговый план починки со спором на «ничего не сломать».
> Основано на аудите кодовой базы (спека от 24.07.2026) и логике `notifier.js`.

---

## TL;DR (за 30 секунд)

Пуши приходят только тебе, потому что **только у твоего аккаунта в базе проставлен `tgUserId`**. Notifier рассылает строго тем, у кого `tgUserId != null` и включены напоминания — а у всех остальных это поле пустое.

Само по себе нажатие «Старт» в боте `tgUserId` **не проставляет**. Механизм, который автоматически привязывает всю базу без ручных действий (авто-capture, «путь C»), **собран локально и на прод не выкачен**. Починка — аккуратно выкатить этот механизм.

Главный риск при выкате — **пересборка лендинга затрёт прод-заглушку `/promo/`** и **не прогнанная миграция `006` может выключить пуши вообще всем, включая тебя**. Оба риска ниже закрыты проверками и порядком шагов.

---

## 1. Как работает рассылка (чтобы понимать, что чиним)

`jobs/notifier.js` запускается по крону **каждую минуту** и делает выборку получателей:

```js
db.user.findMany({
  where: { tgUserId: { not: null }, notifyPrefs: { enabled: true } }
})
```

Получатель попадёт в рассылку **только если выполнены оба условия**:

1. `User.tgUserId != null` — аккаунт в приложении связан с Telegram-аккаунтом.
2. `NotifyPrefs.enabled = true` — тумблер «Напоминания» в Профиле (по умолчанию `true`).

Дальше notifier: считает локальное время юзера в его `NotifyPrefs.timezone` (дефолт `Europe/Moscow`), шлёт только в минуту `:00` и только если час совпал с фазой (**утро 09:00 / день 14:00 / вечер 20:00**), защищается от дублей ключом `lastSlotKey = "YYYY-MM-DD-<phase>"` (фаза стреляет раз в день), выбирает аудиторию (`paid` при активной подписке, иначе `free`) и берёт случайную активную фразу, у которой в поле `phases` есть текущая фаза.

**Важно:** хардкода твоего `chat_id` нигде нет. Ты получаешь пуши не потому, что «зашит» в код, а потому что у тебя единственного проставлен `tgUserId`.

## 2. Root cause — почему только ты

### Основная причина

У всех, кроме тебя, `tgUserId = null`. Они физически не попадают в выборку notifier'а. У тебя поле проставлено с «старой эры» — через legacy-авторизацию в Mini App (`/auth/tg-init`, путь A).

### Почему «нажали Старт» не помогает

Это ключевое заблуждение. Есть три пути, которыми у юзера появляется `tgUserId`, и **обычный `/start` не входит ни в один из них**:

| Путь | Что реально нужно | Статус |
|---|---|---|
| **A. Legacy `/auth/tg-init`** | Открытие Mini App со старой авторизацией по initData. Создаёт отдельный tg-шелл-аккаунт. | Так вышло у тебя. Для новых юзеров как массовый механизм не работает. |
| **B. Deep-link (ручной)** | В Профиле нажать «Подключить Telegram» → получить код (живёт 15 мин) → нажать в боте `/start link_<код>`. Только тогда webhook свяжет аккаунт. | Работает, в т.ч. для PWA-юзеров вне Telegram. Но требует ручного действия. |
| **C. Авто-capture** | Фронт после `WebApp.ready()` тихо шлёт `POST /notify/tg-capture {initData}`, бэк верифицирует HMAC и ставит `tgUserId` текущему залогиненному юзеру. | **Единственный путь, который делает получателями всю базу без кликов. Собран локально, НЕТ на проде.** |

Голый `/start` без `link_<код>` webhook ничем не привяжет. Поэтому люди, которые «нажали Старт», имеют чат с ботом, но их аккаунт в приложении с Telegram не связан — `tgUserId` пустой — пуши не идут.

### Скрытый второй предохранитель

Даже когда `tgUserId` появится, есть второй риск. Notifier шлёт по фазам и читает поле `PushPhrase.phases`, которое заполняется миграцией `006_push_phases.sql` (бэкфилл `08→утро, 12/16→день, 20→вечер`). Если `006` на проде **не прогнан**, у старых фраз `phases` пустой, `parsePhases()` вернёт `[]`, notifier залогирует `no push phrases configured` и не отправит **никому, включая тебя**.

То, что тебе пуши всё-таки доходят, косвенно говорит, что `006` скорее всего уже прогнан. Но полагаться на косвенный признак нельзя — проверяем прямо (см. §3).

## 3. Сначала — диагностика (ничего не меняем, только читаем)

Перед любым деплоем подтверждаем диагноз на проде. Эти запросы **только читают**, ничего не ломают.

```sql
-- 1. Сколько людей реально в выборке рассылки.
--    Ожидание: 1 (только ты). Если так — диагноз подтверждён.
SELECT count(*) AS receivers
FROM "User"
WHERE "tgUserId" IS NOT NULL;

-- 2. Включены ли у них напоминания (второе условие notifier'а).
SELECT count(*) AS enabled_receivers
FROM "User" u
JOIN "NotifyPrefs" p ON p."userId" = u.id
WHERE u."tgUserId" IS NOT NULL AND p.enabled = true;

-- 3. Прогнана ли миграция 006 — есть ли активные фразы с проставленными фазами.
--    Если 0 — это отдельная поломка, пуши не идут вообще никому.
SELECT count(*) AS phrases_with_phases
FROM "PushPhrase"
WHERE active = true
  AND phases IS NOT NULL
  AND phases <> '';

-- 4. Сколько всего юзеров в базе — оценить масштаб «недоохвата».
SELECT count(*) AS total_users FROM "User";
```

Интерпретация:

- Запрос 1 вернул `1` — корень подтверждён: получатель только ты.
- Запрос 3 вернул `0` — миграция `006` не прогнана, это надо чинить обязательно (иначе после выката пуши всё равно не пойдут).
- Запрос 3 вернул `> 0` — фразы в порядке, `006` прогнан.

> Полезно сохранить вывод этих запросов **до** деплоя — это твоя точка отсчёта, чтобы после выката сравнить и увидеть рост числа получателей.

## 4. Решение — безопасный деплой (zero-downtime)

Цель: выкатить путь C (авто-capture) + добить миграции, **не трогая прод-заглушку лендинга**.

### 4.0. Подготовка и страховка (до изменений)

```bash
ssh root@87.228.61.44
cd /opt/meditation-app

# Зафиксировать текущее состояние для отката
git rev-parse HEAD > /tmp/deploy_prev_commit.txt   # запомнить текущий коммит
cat /tmp/deploy_prev_commit.txt

# Бэкап БД перед миграциями (обязательно!)
pg_dump "$DATABASE_URL" | gzip > /tmp/backup_$(date +%Y%m%d_%H%M%S).sql.gz
ls -lh /tmp/backup_*.sql.gz
```

Проверить, что рабочая директория чистая, прежде чем тянуть код:

```bash
git status            # не должно быть локальных незакоммиченных правок на проде
git fetch --all
git log --oneline -5 origin/main   # убедиться, что тянем ожидаемые коммиты
```

### 4.1. Обновить код

```bash
git pull --ff-only    # только fast-forward: если не проходит — на проде расхождение, разбираться, а не форсить
```

### 4.2. Миграции БД (идемпотентны)

```bash
psql "$DATABASE_URL" -f backend/sql/006_push_phases.sql
psql "$DATABASE_URL" -f backend/sql/007_broadcast_channel.sql
```

Миграции идемпотентны (можно прогонять повторно), но бэкап из 4.0 всё равно должен быть сделан.

### 4.3. Backend — поднять `/notify/tg-capture`

```bash
cd backend
npm install
npx prisma generate
cd ..
systemctl restart meditation-api
```

### 4.4. Фронт + CMS

```bash
# application содержит usePlatformAuth с авто-capture — его пересобрать обязательно
cd application && npm install && npm run build && cd ..

# CMS — по необходимости (управление фразами)
cd cms && npm install && npm run build && cd ..
```

### Чего делать НЕЛЬЗЯ

- **НЕ билдить лендинг.** `npm run build:landing` (или любой билд лендинга) **затрёт прод-заглушку `/promo/`**. Собираем только `application` и `cms`.
- **НЕ форсить `git pull`** через reset/merge, если `--ff-only` не прошёл. Расхождение — это сигнал, а не помеха.
- **НЕ пропускать `npx prisma generate`** — без него бэкенд не подхватит новую схему и `/notify/tg-capture` не поднимется.
- **НЕ менять `PUSH_*_HOUR` на проде «на время теста»** и забывать вернуть — иначе реальным юзерам прилетит пуш не в ту фазу.

## 5. Проверка после деплоя (что всё поднялось и никто не сломан)

Проверяем в порядке «от тебя к базе», ничего не рассылая вслепую.

1. **Эндпоинт живой.** Убедиться, что `/notify/tg-capture` отвечает (не 404). Открыть Mini App **залогиненным внутри Telegram** — фронт сам дёрнет capture.

2. **`tgUserId` появился.** После открытия Mini App проверить в БД:

   ```sql
   SELECT id, "tgUserId", "updatedAt"
   FROM "User"
   WHERE "tgUserId" IS NOT NULL
   ORDER BY "updatedAt" DESC
   LIMIT 10;
   ```

   Должны появляться новые записи по мере того, как люди открывают Mini App.

3. **Тест-пуш доходит.** В Профиле нажать «Тест-пуш» (`POST /notify/test`) — приходит фраза фазы «день» немедленно. Это подтверждает, что транспорт (relay + токен) жив.

4. **Фразы настроены.** В CMS убедиться, что есть активные фразы с проставленными фазами для обеих аудиторий (`free` и `paid`). Иначе notifier залогирует `no push phrases configured`.

5. **Реальная фаза.** Дождаться ближайшей фазы (09:00 / 14:00 / 20:00 по TZ юзера) и проверить логи notifier'а — что рассылка ушла и без ошибок.

6. **Сравнить с точкой отсчёта.** Повторить запрос 1 из §3 — число получателей должно расти относительно того, что было до деплоя.

### Кто и когда станет получателем

- **Открыл Mini App внутри Telegram хотя бы раз** — сработал авто-capture — станет получателем автоматически.
- **Чистый PWA / браузер-юзер** (в Telegram Mini App не заходит) — только ручной deep-link (путь B): «Подключить Telegram» в Профиле.

## 6. Транспорт в РФ — отдельная точка отказа

`utils/tgBot.js` ходит не напрямую на `api.telegram.org` (прямой Bot API в РФ режется DPI), а через **relay** (Cloudflare Worker / VPS вне РФ, `deploy/tg-relay/`) с shared-secret `X-Relay-Auth = TG_RELAY_SECRET`. Нужен валидный `TG_BOT_TOKEN`.

Если relay или токен отвалятся — **отправка упадёт всем, включая тебя**. Поэтому «Тест-пуш» в §5 — важная проверка: он подтверждает, что этот канал живой. Env-переменные `TG_BOT_TOKEN`, `TG_RELAY_SECRET`, `TG_API_BASE` должны быть на месте после рестарта.

## 7. План отката (если что-то пошло не так)

Изменения аддитивные и малорисковые, но план отката держим наготове:

- **Миграции.** `006`/`007` идемпотентны и только добавляют/бэкфиллят данные. Полный откат данных — из бэкапа `/tmp/backup_*.sql.gz` (см. 4.0). Отдельные миграции откатывать вручную обычно не требуется.
- **Код.** Вернуться на прежний коммит:

  ```bash
  cd /opt/meditation-app
  git checkout $(cat /tmp/deploy_prev_commit.txt)
  cd backend && npm install && npx prisma generate && cd ..
  systemctl restart meditation-api
  ```

- **Быстрый «стоп рассылки» без отката кода.** Если нужно срочно прекратить пуши, не откатываясь: выключить крон notifier'а / остановить сервис, либо на уровне БД временно снять флаг у затронутых `NotifyPrefs`. Не удаляй `tgUserId` — это потеря привязок.
- **Заглушка лендинга.** Если её случайно затёрли билдом — восстановить `/promo/` из бэкапа/репозитория заглушки. Поэтому проще вообще не билдить лендинг (см. §4).
